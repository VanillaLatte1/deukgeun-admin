# 작업별 실행·검증 절차

이 문서는 [AGENTS.md](../AGENTS.md)의 실행 선택 기준이다. 단계 번호는 권한이 아니다.
요청 범위와 환경을 먼저 확인하고, 필요한 최소 단계를 선택한다.
기존 승인을 다시 받지 않으며, 새 외부 변경이 필요할 때만 정확한 대상과 영향을 확인한다.

## 실행 수준

| 수준 | 적용할 작업 | 수행 범위 | 전제·완료 증거 |
| --- | --- | --- | --- |
| L0 | 분석, 문서, 정책 정리, 읽기 전용 리뷰 | 관련 소스·참조 경로·diff·공백 검사 | 실행 검증과 소스 추론을 구분. 문서만 바뀌면 여기서 완료 가능 |
| L1 | 컴포넌트·Action·타입 등 소스 변경 | 변경 파일 ESLint, 필요 시 프로젝트 타입 검사 | 설치된 로컬 도구 사용. 실패 원인과 변경 관련성 확인 |
| L2 | 라우팅·인증·공유 구성·여러 화면의 동작 변경 | 필요 시 전체 lint/build, 관련 화면과 사용자 흐름 확인 | DB 대상 확인. 저장 검증은 승인된 테스트 데이터/환경에서만 수행 |
| L3 | SQL 적용, seed/import, 실제 데이터 변경, 배포·외부 설정 | 명시적으로 승인된 작업만 실행하고 결과 확인 | 대상 환경·영향 범위·복구 방법 확인. build 통과만으로 배포/업무 성공을 선언하지 않음 |

커밋·푸시·머지는 검증 단계에 포함되지 않는다. 별도 명시적 요청이 있어야 수행한다.
순수한 코드 수정 요청이 연결된 DB에 시험 데이터를 만들거나 운영 배포할 권한을 주지는 않는다.

## 시작과 L0

저장소 루트의 PowerShell에서 필요한 명령만 실행한다.

```powershell
git status --short
git diff --stat
git diff --check
```

`git diff`는 추적되지 않은 새 파일을 포함하지 않는다. 새 파일은 별도로 읽어 내용·상대
링크·참조 경로를 확인한다. 의존성 설치, 개발 서버 시작, 빌드는 L0의 필수 조건이 아니다.
현재 런타임이 필요하면 `node --version`, `npm --version`으로 확인하되 버전 변경은 분리한다.

## L1: 설치된 도구로 정적 검사

아래는 회원 Action 변경의 예다. 파일 목록은 실제 변경 범위로 바꾼다.

```powershell
npm run lint -- src/app/members/actions.ts
```

타입 영향이 있으면 로컬 TypeScript 바이너리를 직접 사용한다.
`npx`의 자동 다운로드에 기대지 않는다.

```powershell
& .\node_modules\.bin\tsc.cmd --noEmit --incremental false
```

- 저장소에는 별도 `npm run typecheck`나 `npm test`가 없다.
- `node_modules`가 없으면 미실행 이유를 보고한다. 코드 작업의 검증을 위해 설치가
  필요한 경우 요청 범위와 설치 영향을 판단하고, lockfile 재현에는 `npm ci`를 사용한다.
  기존 `node_modules`를 교체하며 lifecycle script와 네트워크 접근이 발생할 수 있다.
- 문서만 수정하는 작업에서 검증 도구를 설치하지 않는다. 테스트 프레임워크도 필요성이
  확인되기 전에는 추가하지 않는다.
- 생성된 Next 타입이 필요한 오류라면 원인을 확인하고 필요한 L2 절차를 선택한다.
  타입 검사 실패를 없애기 위해 `tsconfig.json`의 검사 범위를 축소하지 않는다.

## L2: 빌드와 사용자 흐름

전체 정적 검사가 필요한 변경:

```powershell
npm run lint
npm run build
```

화면 확인이 필요한 경우:

```powershell
npm run dev
```

빌드 산출물을 직접 확인할 때는 성공한 build 이후 `npm run start`를 사용한다.
서버 기동 전에 포트 사용 여부와 DB 대상 환경을 확인한다. 다른 작업의 서버를 종료하지
않으며, 자신이 시작한 프로세스만 정리한다. 빌드·렌더링이 외부 자원이나 서버 데이터에
접근할 가능성도 고려한다. `.env` 또는 환경 변수 이름만으로 개발/운영을 판단하지 않는다.

인증된 화면을 열려면 실제 로그인 세션이 필요하다. 임의 쿠키를 발급하거나 인증을
우회해 검증하지 않는다. 자격 증명/테스트 환경이 없으면 가능한 정적 검증을 마치고,
실제 사용자 흐름을 확인하지 못했다는 점을 보고한다.

### 변경 범위별 확인 사례

실행된 자동 테스트 목록이 아니라, 해당 기능 변경 시 고르는 검증 사례다.
읽기 전용 확인과 저장·삭제 검증을 구분한다.

| 변경 영역 | 확인 사례 | 완료 판단 |
| --- | --- | --- |
| UI·CSS | 데스크톱/좁은 화면, 메뉴·모달·키보드 포커스, pending·오류·성공 상태 | 관련 화면의 표시와 상호작용 확인; 인쇄 변경은 인쇄 미리보기까지 |
| 인증·proxy | 비로그인 보호 경로, 잘못된 로그인, 정상 로그인·로그아웃, 만료/변조 쿠키, 새 API의 보호 여부 | 리다이렉트·쿠키·서버 접근 제어를 구분해서 확인 |
| 회원·목표 | 필수값·잘못된 숫자·증적 날짜, 등록/수정 후 재조회, 회원 성공+목표 실패 | 저장 필드와 목표가 함께 유지되는지 확인; 부분 실패를 성공으로 표시하지 않음 |
| 운동 인증 | 일반 0/1분·사진 1/2장, 러닝 29/30분·사진 1장, 동일 주 회차 중복, 수정 시 자기 제외, 유형 전환 | UI와 서버 조건 일치, 저장 후 조회 및 관련 집계 일치 |
| 이미지 | 첨부 교체/취소, 업로드 실패, DB 저장 실패, 만료 URL, 이관 기록의 누락 이미지 | 행과 파일 상태를 각각 확인; 실패 후 무조건 재전송하지 않음 |
| 주차·제외 | 토요일/일요일, 연말/연초, Asia/Seoul과 UTC, 제외 등록·해제, 조회 실패 | 조회 범위·회차 중복·대시보드·벌금이 같은 주차 기준 사용 |
| 벌금·정산 | 아래 계산 예, 반기 경계·종료일, 증적 월 밖 날짜, 과거 반기 조회 | 소스 계산과 화면 금액 일치; 운영 정책과의 합의는 별도 |
| SQL | 현재 컬럼·제약·중복·RLS, 예상 영향 행, 변경 후 재조회·업무 흐름 | 실제 승인된 대상에 적용한 사실과 검증 범위를 기록 |

### 정산 계산 기준 예

현재 소스를 바꾸지 않는 회귀 검증용 예다. 운영 회원 대신 가상 입력으로 확인한다.

| 입력 | 현재 코드의 기대 결과 |
| --- | --- |
| 주 목표 3회, 두 주 실적 각각 2회/0회, 제외 없음 | 미달 2주, 주간 벌금 20,000원 |
| 위 조건에서 0회인 주를 제외 | 미달 1주, 주간 벌금 10,000원 |
| 주 목표 0회 | 주간 미달 벌금 0원 |
| 개인 벌금 100,000원, 최종 목표 달성 | 최종 벌금 0원 |
| 미달성, 증적 여부 true, 날짜가 해당 반기 증적 월 안 | 최종 벌금 50,000원 |
| 미달성, 증적 없음 또는 증적 월 밖 날짜 | 최종 벌금 100,000원 |
| 주간 벌금 20,000원 + 최종 벌금 50,000원 | 총액 70,000원 |

날짜 예: `2026-06-27`은 `2026-06-21` 주차, `2026-06-28`은 다음 주차다.
2026년 상반기 운동 집계는 6월 27일까지지만, 월말 증적 기간은 6월 30일까지다.

## 실패 시 복구와 중단 기준

| 현상 | 먼저 확인 | 안전한 후속 작업 / 중단 기준 |
| --- | --- | --- |
| 로컬 도구·환경 변수 없음 | 설치 여부, 설정 이름, 필요한 단계 | 가능한 L0를 완료. 비밀값을 만들거나 운영 설정을 복사하지 않음 |
| lint/type/build 실패 | 첫 원인, 변경 관련성, 기존 실패 여부 | 관련 원인을 수정한 뒤 재실행. 무관한 의존성 업데이트·검사 해제 금지 |
| `42703`, `PGRST204`, `42P10` | 누락 컬럼, 스키마 캐시, conflict 제약과 기존 fallback | 실제 스키마와 적용 SQL 확인. DB 변경 권한이 없으면 SQL 준비·영향 설명까지 |
| 회원 저장 후 오류 | 회원 행과 목표 행 각각의 저장 여부 | 상태 확인 후 필요한 단계만 재시도. 중복 회원 삭제로 임의 복구하지 않음 |
| 업로드/인증 저장 실패 | 업로드 경로, DB 행, 네트워크·오류 응답 | 부분 성공 확인 전 재업로드·파일 삭제 중단 |
| 주간 제외가 갑자기 사라짐 | 조회 오류 로그와 테이블/권한 상태 | 빈 배열을 실제 면제 없음으로 확정해 벌금을 안내하지 않음 |
| 배포 또는 alias 실패 | 배포 URL/상태, alias의 현재 대상 | 이미 생성된 배포 확인 전 전체 배포를 반복하지 않음 |
| 대상 DB·서비스가 불명확 | 프로젝트 식별자, 연결 설정의 대상 | 외부 변경만 중단하고 로컬 분석·수정·SQL 초안을 마침 |

## L3와 완료 기록

실제 배포는 [배포 가이드](deployment-guide.md)를 참고하되, `npm run deploy:prod`를
빌드 검증 명령으로 사용하지 않는다. SQL·seed·import는 dry-run이 아니며 기존 데이터를
수정할 수 있다. DB 변경 전에는 필요한 백업·영향 행 확인·복구 수단을 준비한다.

완료 보고에는 다음을 포함한다. 실행하지 않은 단계는 생략하거나 미실행 이유를 쓴다.

- 결과: 무엇이 바뀌었고 어떤 요청을 충족했는지.
- 검증: 선택한 수준, 실제 실행 명령, 성공/실패/미실행과 그 근거.
- 산출물: 변경 파일 또는 확인한 결과의 위치.
- 남은 항목: 미확인 사용자 흐름·환경, 부분 실패, 필요한 다음 조치.

예: `L0 완료 — 문서 참조와 diff 공백 검사 통과. 앱 빌드·로그인·DB 저장은 미실행.`
